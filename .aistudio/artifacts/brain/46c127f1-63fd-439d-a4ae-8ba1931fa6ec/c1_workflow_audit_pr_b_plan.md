Finding 1 [CRITICAL]: Host Runner Escape via Writable .git Volume Mount
--------------------------------------------------------------------------------
File: .github/workflows/brain-build.yml
Lines: 341-347 & Lines 563-574

Code Excerpt:
  345: "run_args": ["--rm", "--user", f"{os.getuid()}:{os.getgid()}", "-e", "HOME=/tmp", "-v", f"{os.environ['GITHUB_WORKSPACE']}:/workspace"],
  ...
  570: git commit -m "Brain ${COMMAND}: automated candidate"

Root Cause:
  The agent container mounts GITHUB_WORKSPACE at /workspace read-write with the host
  UID/GID. GITHUB_WORKSPACE contains the checked-out target repository including its
  .git directory. An untrusted coding agent or prompt injection payload can create an
  executable file at /workspace/.git/hooks/pre-commit or configure core.hooksPath in
  .git/config. Later in the same workflow, step 'publish' executes `git commit` directly
  on the GitHub Actions host runner outside Docker. When `git commit` runs, Git executes
  .git/hooks/pre-commit on the host VM.

Impact:
  Arbitrary code execution on the GitHub Actions host runner. The hook inherits the
  execution environment of step 530, where GH_TOKEN (secrets.BRAIN_GITHUB_TOKEN) and
  GH_CONTROL_TOKEN (github.token) are present in the step environment. In addition,
  during read-only audit missions (/brain audit), mounting .git read-write allows an
  agent to mutate Git repository internals without detection by `git status --porcelain`.

Proposed Fix:
  1. Move .git out of the workspace before starting the agent:
     mv "$GITHUB_WORKSPACE/.git" /tmp/brain-target-git
  2. After agent completion, assert no .git directory was generated by the agent:
     [ ! -e "$GITHUB_WORKSPACE/.git" ] || { echo "::error::Agent created unexpected .git"; exit 1; }
     mv /tmp/brain-target-git "$GITHUB_WORKSPACE/.git"
  3. Execute all host Git operations with core.hooksPath disabled and hooks bypassed:
     git -c core.hooksPath=/dev/null commit --no-verify ...
  4. For /brain audit missions, pass :ro in Docker run_args for /workspace.

Finding 2 [MAJOR]: Gitleaks Secret Scan Crashes on File Deletions or Renames
--------------------------------------------------------------------------------
File: .github/workflows/brain-build.yml
Lines: 398-403

Code Excerpt:
  399: set -euo pipefail
  400: git diff --name-only -z | tar --null -T - -cf /tmp/brain-changed-files.tar
  401: mkdir -p /tmp/brain-gitleaks-source
  402: tar -xf /tmp/brain-changed-files.tar -C /tmp/brain-gitleaks-source
  403: docker run --rm -v /tmp/brain-gitleaks-source:/src zricethezav/gitleaks:v8.24.2 dir --redact --exit-code 1 /src

Root Cause:
  `git diff --name-only -z` lists all modified, added, and deleted file paths. For any
  deleted file, the file path is emitted in the NUL-separated stream, but the file no
  longer exists on the filesystem. When `tar --null -T -` attempts to stat the deleted
  file, GNU tar emits:
    tar: <filename>: Cannot stat: No such file or directory
    tar: Exiting with failure status due to previous errors
  and exits with code 2. Because `set -e` and `pipefail` are active, the step crashes.

Impact:
  Any mission that deletes or renames a file crashes unconditionally at the secret
  scanning stage. No candidate PR is generated, and no failure issue comment is posted.

Proposed Fix:
  Filter out deleted files from the stream using `--diff-filter=d`:
  git diff --name-only --diff-filter=d -z | tar --null -T - -cf /tmp/brain-changed-files.tar
  (Verified: GNU tar on an empty stream creates a valid archive with exit code 0;
  extracting an empty archive succeeds with exit code 0; and gitleaks scans an empty
  source directory cleanly with 0 leaks).

Finding 3 [MAJOR]: Silent Workflow Termination (No Issue Reporting on Failures)
--------------------------------------------------------------------------------
File: .github/workflows/brain-build.yml
Lines: 532, 551, 578

Code Excerpt:
  532: if: always() && steps.agent.outcome == 'success' && (needs.prepare.outputs.command == 'audit' || (steps.checks.outcome == 'success' && steps.gitleaks.outcome == 'success'))
  ...
  578: GH_TOKEN="$GH_CONTROL_TOKEN" gh issue comment "$ISSUE_NUMBER" ...

Root Cause:
  The only issue comments in the entire workflow exist inside step 'publish' (lines 551
  and 578). Step 'publish' is strictly gated on every preceding stage succeeding. There
  is no fallback failure reporting step.

Impact:
  If the lease queue times out, if model credentials are missing, if the agent fails or
  times out, if whitespace errors trigger git diff --check, if gitleaks detects secrets,
  or if tests fail, the workflow exits with zero feedback on the triggering issue. Users
  working from mobile devices receive no notification or diagnosis.

Proposed Fix:
  Add an always()-executed failure notification step:
  `if: always() && failure() && needs.prepare.outputs.issue_number != ''`
  Using GH_CONTROL_TOKEN to comment on the initiating issue with the run URL and the
  name of the failed step, without disclosing secret values.

Finding 4 [MAJOR]: tr Expression Corrupts File Names and Warning Messages
--------------------------------------------------------------------------------
File: .github/workflows/brain-build.yml
Lines: 566-567

Code Excerpt:
  566: files_changed="$(git diff --cached --name-only | head -8 | tr '\\n' ',')"
  567: warnings="$(grep '^WARN:' /tmp/brain-checks.log | head -2 | tr '\\n' ';' || true)"

Root Cause:
  In a YAML block scalar (`run: |`), bash receives the literal command `tr '\\n' ','`.
  Inside bash single quotes (`'...'`), backslashes have no escape behavior. Bash passes
  two characters (`\` and `n`) to tr as set 1. tr translates every backslash and every
  letter `n` into commas or semicolons, leaving literal newline characters untouched.
  - `main.py` is transformed into `mai,.py`.
  - Check warnings containing the letter `n` are mutilated (e.g. `WARN: ;o Pytho; ...`).
  - Unescaped newlines remain in the variables, causing multiline argument corruption
    in `gh pr create` and `gh issue comment`.

Impact:
  Corrupts candidate PR descriptions, issue comments, and command line arguments.

Proposed Fix:
  Use standard POSIX `paste`:
  files_changed="$(git diff --cached --name-only | head -8 | paste -sd, -)"
  warnings="$(grep '^WARN:' /tmp/brain-checks.log | head -2 | paste -sd';' - || true)"
  (Verified: `paste -sd, -` produces clean comma-delimited strings without trailing commas).

Finding 5 [MINOR]: git diff --check Terminate Agent Step Abruptly on Whitespace
--------------------------------------------------------------------------------
File: .github/workflows/brain-build.yml
Lines: 375, 380

Code Excerpt:
  375: set -e
  ...
  380: git diff --check

Root Cause:
  Line 375 re-enables `set -e`. Line 380 runs `git diff --check`. If any trailing
  whitespace exists in modified files, `git diff --check` exits with status 2. Under
  `set -e`, this immediately aborts the step before lines 386-387 run, preventing
  diff-stat and patch generation.

Impact:
  Cosmetic whitespace causes an unhandled step crash without an error summary.

Proposed Fix:
  Run as a non-fatal warning:
  git diff --check || echo "::warning::Whitespace errors detected in agent changes."

Finding 6 [MINOR]: Trigger Expression Allows Unintended Suffixes
--------------------------------------------------------------------------------
File: .github/workflows/brain-build.yml
Lines: 45-47, 55-60

Code Excerpt:
  startsWith(github.event.issue.body, '/brain build') ||
  startsWith(github.event.issue.body, '/brain fix') ||
  startsWith(github.event.issue.body, '/brain audit')
  ...
  startsWith(github.event.comment.body, '/brain retry') &&

Root Cause:
  `startsWith` matches any string with that prefix, including `/brain builder`,
  `/brain build-all`, or `/brain retry-now`.

Impact:
  Spurious comments trigger GitHub Actions runners, consume build minutes, and fail
  inside the Python validation step.

Proposed Fix:
  Constrain YAML expressions to check for exact match, trailing whitespace, or newline
  boundaries, and update `tests/test_brain_build_workflow_contract.py` in sync.

Finding 7 [MINOR]: Misleading Test Reporting When Target Has No Tests
--------------------------------------------------------------------------------
File: .github/workflows/brain-build.yml
Lines: 421-422, 444-449, 574, 578

Root Cause:
  When a target repo contains no test suite, the workflow runs `compileall` or emits a
  warning and exits 0, but line 574 unconditionally states:
  `- Checks: project checks and gitleaks passed.`

Impact:
  Reviewers are misled into believing full unit/integration tests executed and passed.

Proposed Fix:
  Export `check_type` from the checks step and accurately reflect fallback status
  (e.g. `compileall smoke check (no tests found)`) in candidate PRs and comments.
